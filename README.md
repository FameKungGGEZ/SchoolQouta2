# ระบบสมัครโควตา ม.4 โรงเรียนตะพานหิน

เว็บสมัครนักเรียนแบบ responsive สำหรับกรอกใบสมัคร อัปโหลดเอกสาร และให้ครูตรวจสอบ เชื่อมต่อ Supabase Auth, Database และ private Storage โดยใช้ publishable key ในหน้าเว็บและบังคับสิทธิ์ด้วย RLS

## ตั้งค่า Supabase

1. ใช้ Supabase project ที่กำหนดไว้ใน `supabase-client.js` หรือแก้ `SUPABASE_URL` และ `SUPABASE_PUBLISHABLE_KEY` ให้ตรงกับโปรเจกต์ของโรงเรียน ค่า publishable key ใช้ในเว็บได้ แต่ห้ามนำ `service_role` key มาใส่ในไฟล์หน้าเว็บ
2. ใช้ Supabase CLI รัน `supabase link --project-ref gvkwltjcbiweuzaalbuw` แล้ว `supabase db push` เพื่อใช้ migration ทั้งหมดใน `supabase/migrations/` ตามลำดับเวลา รวมถึงการปรับสถานะตรวจเอกสารและการจัดเก็บใบสมัคร PDF
3. สร้างผู้ใช้ในหน้า Supabase Dashboard > Authentication > Users แล้วเพิ่มแถวใน `public.profiles` ผ่าน SQL Editor โดยใช้ user ID จาก Auth:

   ```sql
   insert into public.profiles (user_id, role, student_id, full_name, class_room, seat_number)
   values ('AUTH_USER_UUID', 'admin', null, 'ชื่อผู้ดูแล', null, null);
   ```

   สำหรับนักเรียนให้ใช้ `role = 'student'` และระบุ `student_id` 5 หลักที่ไม่ซ้ำ รวมถึงชื่อและห้องเรียน ส่วนครูใช้ `role = 'teacher'` และ `student_id = null` บัญชีและข้อมูลจริงต้อง provision โดยผู้ดูแลที่เชื่อถือได้
4. เปิดเว็บผ่าน local/static server หรือ deploy ไป Vercel; อย่าเปิดด้วย `file://` เมื่อต้องทดสอบ Auth redirect/session

นักเรียนเข้าสู่ระบบด้วยเลขประจำตัว 5 หลักและวันเกิดรูปแบบ `วว/ดด/ปปปป` โดยไม่ต้องมีอีเมลจริง เว็บแมปเลขประจำตัวเป็นอีเมลภายในรูปแบบ `student-{เลขประจำตัว}@login.schoolquota.invalid` สำหรับ Supabase Auth; ผู้ดูแลต้องสร้างบัญชี Auth ด้วย alias นี้และตั้งวันเกิดเป็นรหัสผ่าน จากนั้นเพิ่ม profile ตามข้อ 3 ครูและผู้ดูแลยังใช้อีเมลกับรหัสผ่านของ Supabase Auth บัญชีที่ไม่มี profile หรือ role ที่ตรงกับหน้าที่จะเข้าใช้ไม่ได้

นักเรียนแก้ไขใบสมัครได้ขณะเป็นฉบับร่างหรือถูกขอให้แก้ไข การส่งใบสมัครจะตรวจเอกสารในฐานข้อมูลและ Storage ซ้ำที่ฝั่ง server

เมื่อนักเรียนกรอกข้อมูลและอัปโหลดรูปถ่าย ปพ.1 และใบรับรองครบ ระบบจะสร้าง PDF จากแบบฟอร์มต้นฉบับ `application-template.html` ซึ่งใช้โครงหน้าและรูปแบบเดียวกับไฟล์ HTML อ้างอิง แล้วอัปโหลดเข้า private Storage ก่อนบันทึกสถานะส่งตรวจและลิงก์ไฟล์ในฐานข้อมูลด้วย RPC เดียว ครูจะแสดงเฉพาะ PDF ที่บันทึกใน Storage แล้วเท่านั้น รายการรอตรวจเก่าที่ไม่มีไฟล์จะสร้างและบันทึก PDF ก่อนเปิดให้ดู

เมื่อครูขอให้นักเรียนแก้ไข นักเรียนส่งเอกสารใหม่แทนไฟล์เดิมได้ ระบบจะเปลี่ยน path ในใบสมัครหลังอัปโหลดไฟล์ใหม่สำเร็จ แล้วจึงลบไฟล์เก่าชนิดเดียวกัน หากบันทึก path ไม่สำเร็จ ระบบจะลบไฟล์ใหม่ที่ยังไม่ได้ใช้อ้างอิงและคงไฟล์เดิมไว้ การส่งตรวจซ้ำจะสร้าง PDF ใหม่จากข้อมูลและเอกสารล่าสุด ส่วนตอนครูอนุมัติ ระบบจะสร้าง PDF ฉบับสุดท้ายจากข้อมูลล่าสุดพร้อมเลขลำดับ และเก็บไฟล์นั้นให้นักเรียนดาวน์โหลดจากหน้าสถานะได้ ครูเปิดดูหรือดาวน์โหลดเอกสารที่เคยส่งแล้วได้จากเมนู “นักเรียนทั้งหมด” แม้ผลตรวจเป็นผ่านหรือไม่ผ่าน โดยเป็นโหมดอ่านอย่างเดียว เมื่อไม่ผ่าน ระบบถอดการอ้างอิงและลบเฉพาะ PDF ใบสมัคร ส่วนเอกสารต้นทางยังคงอยู่ การส่งจะถูกปฏิเสธทั้งฝั่งเว็บและฐานข้อมูลหากข้อมูลหรือเอกสารไม่ครบ

## สร้างข้อมูลทดสอบ

สคริปต์ `scripts/seed-demo-data.mjs` แบบปกติสร้างนักเรียนสมมติ 100 คน รอตรวจ 30 ผ่าน 10 ไม่ผ่าน 10 และอีก 50 คนยังไม่มีใบสมัคร ส่วนโหมด `--small-demo` สร้างนักเรียนเพิ่มอีก 20 คน (รหัส `99201`–`99220`) แบ่งเป็นมีบัญชีอย่างเดียว 4 คน, ข้อมูลใบสมัครฉบับร่าง 4 คน, รอตรวจ 4 คน, ผ่าน 4 คน และไม่ผ่าน 4 คน โดย 12 ใบสมัครที่ส่งแล้วมีเอกสารทดสอบคนละ 3 ไฟล์ ภาพใน `test-data/demo-documents/` เป็นภาพวาด/เอกสาร placeholder ที่สร้างขึ้นสำหรับทดสอบ ไม่ใช่รูปบุคคลหรือเอกสารจริง

ตรวจจำนวนข้อมูลโดยไม่เชื่อมต่อฐานข้อมูล:

```powershell
node .\scripts\seed-demo-data.mjs --dry-run
.\scripts\seed-small-demo.ps1 -DryRun
```

เพื่อ seed ชุด 20 คนไปยัง Supabase ให้รันตัวช่วยนี้จาก PowerShell; ระบบจะถาม `service_role` key แบบซ่อนการพิมพ์, ใช้เฉพาะระหว่างการรัน แล้วคืน/ล้างตัวแปรแวดล้อมเดิม ห้ามส่ง key ในแชตหรือใส่ในไฟล์โค้ด:

```powershell
.\scripts\seed-small-demo.ps1
```

สคริปต์สร้าง Auth users ภายใน, profiles, ใบสมัคร และอัปโหลดไฟล์ไปยัง private bucket โดยไม่เขียน service key ลงดิสก์ สร้างไฟล์เข้าสู่ระบบทดสอบ `test-data/demo-student-logins.csv` ซึ่งถูก `.gitignore` ไว้; เก็บไฟล์นี้ไว้เฉพาะในสภาพแวดล้อมทดสอบ และลบข้อมูลทดสอบก่อนใช้งานจริง สคริปต์จะปฏิเสธการเขียนทับบัญชีหรือใบสมัครที่ไม่ได้ทำเครื่องหมายเป็นข้อมูลทดสอบ

## ความปลอดภัยและข้อมูลทดสอบ

- ตารางและ bucket ใช้ RLS; ไฟล์เอกสารเป็น private และเปิดผ่าน signed URL อายุสั้น
- การล็อกอินด้วยวันเกิดเป็นรูปแบบเดิมที่มีความเสี่ยงเพราะเดาง่าย ควรเปิด CAPTCHA/จำกัดอัตราการลองล็อกอิน และจำกัดผู้ที่เข้าถึงข้อมูลผู้สมัคร
- ห้ามเปิดเผย service-role key
- `test-data/school-quota-test-data.xlsx` เป็นข้อมูลสมมติสำหรับทดสอบเท่านั้น ห้ามนำเข้าเป็นข้อมูลจริง
- ก่อนใช้งานจริง ให้ตรวจสอบนโยบาย retention, consent, การกำหนดผู้ตรวจ และการสำรองข้อมูลของโรงเรียน

## เปิดดู

เปิด `index.html` ผ่าน local/static server หรือ deploy โฟลเดอร์นี้ไปยัง Vercel ได้เลย `vercel.json` รองรับเส้นทาง `/admin/login` และ `/admin`

## นำเข้ารายชื่อนักเรียน

ผู้ดูแลหรือครูเปิดเมนู “นำเข้าข้อมูลนักเรียน” แล้วเลือกไฟล์ CSV, XLSX หรือ XLS ที่มีหัวตารางรหัสประจำตัว, คำนำหน้า, ชื่อ, สกุล, วันเกิด, ห้อง และเลขที่ ระบบแสดงตัวอย่างและตรวจรหัสซ้ำ/ข้อมูลผิดก่อนส่งได้ครั้งละไม่เกิน 500 คน

การนำเข้าทำผ่าน Supabase Edge Function `import-students` ซึ่งตรวจ session และ role ฝั่ง server; service-role key ไม่อยู่ในเว็บ นักเรียนใหม่จะได้บัญชี Auth ภายใน, profile, ใบสมัครฉบับร่าง และสถานะเริ่มต้น หากนำเข้ารหัสเดิม ระบบปรับข้อมูลบัญชีและวันเกิดตามไฟล์ โดยไม่เขียนทับใบสมัครหรือผลตรวจเดิม วันเกิดในไฟล์ใช้เป็นรหัสผ่านตามระบบเข้าสู่ระบบเดิมและไม่บันทึกเป็นคอลัมน์วันเกิดแบบอ่านข้อความได้
